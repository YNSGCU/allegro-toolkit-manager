# ATM - 避坑指南

从实际开发中踩过的坑总结的经验。

---

## 1. PowerShell vs CMD 的陷阱

### && 运算符不支持

PowerShell 不支持 `&&`，这是最常踩的坑。

```powershell
# ❌ 在 PowerShell 中会报错
cd D:\xxx && npm install

# ✅ 正确（分号分隔）
cd D:\xxx; npm install

# ✅ 或者在 CMD 中用 &&
cmd
cd /d D:\xxx && npm install
```

### npx 命令执行策略

PowerShell 默认禁止运行脚本文件（.ps1），所以 `npx` 命令会报：
```
无法加载文件 C:\Program Files\nodejs\npx.ps1，因为在此系统上禁止运行脚本
```

```powershell
# ❌ 在 PowerShell 中
npx vite        # 报错

# ✅ 加 .cmd 后缀
npx.cmd vite

# ✅ 或者切换到 CMD
cmd
npx vite
```

### 环境变量设置

```powershell
# PowerShell 语法
$env:VAR_NAME = "value"

# CMD 语法
set VAR_NAME=value
```

## 2. Electron 启动的坑

### 从后台工具无法启动 GUI

我的工具（AI 工具环境）无法启动 Electron，因为 Electron 需要交互式桌面会话。

**症状：**
```
electron_1.app.whenReady().then(() => {
               ^
TypeError: Cannot read properties of undefined (reading 'whenReady')
```

**原因：** 后台进程没有桌面会话权限，Electron 的 `app` 模块无法初始化。

**解决方法：** 每次在 CMD 或 PowerShell 中手动运行。

### npx electron 和直接 electron.exe 的行为差异

```powershell
# 方式 A：通过 npx（推荐）
npx.cmd electron dist-electron/electron/main.js

# 方式 B：直接 electron.exe（环境不同可能导致 app 未定义问题）
node_modules\electron\dist\electron.exe dist-electron\electron\main.js
```

推荐使用方式 A。

### 环境变量必须传对

启动 Electron 时必须设置 `VITE_DEV_SERVER_URL`，否则会尝试加载 `file://` 路径导致白屏。

```powershell
$env:VITE_DEV_SERVER_URL = "http://localhost:5173/"
# 必须和 Vite 实际使用的端口一致！
```

### webSecurity: false 的安全警告

```
Electron Security Warning (Disabled webSecurity)
Electron Security Warning (Insecure Content-Security-Policy)
```

这些警告在开发阶段是正常的，打包后不会显示。
生产环境需要正确处理 CSP 和禁用 `webSecurity: false`。

## 3. React 开发陷阱

### 渲染进程中没有 process.env

Electron 的 `contextIsolation: true` 模式下，渲染进程是纯浏览器环境。
不能使用 `process.env.XXX`。

**症状：**
```
Uncaught ReferenceError: process is not defined
```

**解决：** 环境变量必须通过 IPC 从主进程获取。
```typescript
// ❌ 错误
process.env.USERPROFILE

// ✅ 正确
const result = await window.atm.getEnvVars(['USERPROFILE']);
```

### preload 不执行/注入失败

如果 `window.atm` 是 `undefined`：

1. 检查 preload 路径是否正确（`dist-electron/electron/preload.js` 必须存在）
2. 确认编译步骤已执行（`npx.cmd tsc -p tsconfig.electron.json`）
3. 在 Console 中看是否有 `[ATM Preload]` 日志输出

### 页面白屏排查步骤

1. 按 `Ctrl+Shift+I` 打开 DevTools
2. 在 Console 中输入 `location.href` 确认当前地址
3. 如果地址是 `chrome-error://chromewebdata/` → Vite 没运行或环境变量没传
4. 如果地址是 `http://localhost:5173/` 但白屏 → 看 Console 是否红色错误

## 4. 类型系统陷阱

### EnvEntry.type 和 HotkeyBinding.type 不一致

`EnvEntry.type` 包含 `'funckey' | 'alias' | 'raw' | 'comment' | 'blank'`
`HotkeyBinding.type` 只包含 `'funckey' | 'alias'`

在从 `EnvEntry[]` 构建 `HotkeyBinding[]` 时需要类型断言：
```typescript
const entryType = entry.type as 'funckey' | 'alias';
```

### 主进程和渲染进程用不同的 tsconfig

- `tsconfig.json` — 渲染进程（React），`module: "ESNext"`, `noEmit: true`
- `tsconfig.electron.json` — 主进程，`module: "CommonJS"`, `outDir: "dist-electron"`

新建文件时注意对应的 tsconfig 的 `include` 配置。

## 5. 文件系统陷阱

### 空路径处理

`path.normalize('')` 返回 `'.'`（当前目录），不是空字符串。
检查文件访问时必须先判断路径是否为空：
```typescript
if (!targetPath || targetPath.trim() === '') {
  return { exists: false, readable: false, writable: false };
}
```

### 文件末尾换行

`'abc\n'.split('\n')` 返回 `['abc', '']`，最后一个空元素是 trailing newline 产生的。
解析器需要特殊处理：
```typescript
// 去掉末尾空行（文件以换行结尾时 split 会多出一个空元素）
const lines = rawLines.length > 1 && rawLines[rawLines.length - 1] === ''
  ? rawLines.slice(0, -1)
  : rawLines;
```

### UTF-8 和非 ASCII 字符

- Node.js 的 `fs.readFileSync` / `writeFileSync` 支持 UTF-8
- 中文注释、中文路径、特殊字符在 UTF-8 下都正常
- 关键是要指定 `{ encoding: 'utf-8' }`

## 6. 测试陷阱

### 测试间相互影响

如果多个测试共享 `TEST_TMP_DIR`，前一个测试创建的文件会影响后一个测试的断言。
**解决：** 每个需要隔离的测试使用 `path.join(os.tmpdir(), 'prefix-' + Date.now())`。

### 环境变量在测试中的持久化

`process.env.HOME = xxx` 会修改当前进程的环境变量，可能影响后续测试。
**解决：** 修改前保存旧值，修改后恢复：
```typescript
const oldHome = process.env.HOME;
process.env.HOME = tempDir;
// ... 测试代码 ...
process.env.HOME = oldHome;
```

### 空字符串分割

`''.split(/\r?\n/)` 返回 `['']`，不是 `[]`。
解析器入口需要特殊处理空内容。

## 7. npm install 的坑（国内用户）

### Electron 下载失败

**症状：**
```
RequestError: connect ECONNREFUSED 127.0.0.1:443
```

**原因：** Electron 安装时从 GitHub 下载二进制文件，国内访问不稳定或被屏蔽。

**解决：**
```powershell
# 方案 1：每次安装时指定镜像
$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
npm install --registry=https://registry.npmmirror.com

# 方案 2：创建 .npmrc 文件（推荐，一劳永逸）
# 文件内容：
# registry=https://registry.npmmirror.com
# electron_mirror=https://npmmirror.com/mirrors/electron/
```

### EPERM 权限错误

**症状：**
```
EPERM: operation not permitted, rmdir '...\@babel\core\lib\config'
```

**原因：** Windows 文件锁冲突，通常发生在多次 npm install 操作之间。

**解决：**
1. 等一会再重试 `npm install`
2. 或者删除 `node_modules` 后重试

## 8. 版本兼容性

### Electron v35 和 Node.js

- Electron v35 内置 Node.js v22.x
- `npx electron --version` 可能显示的是 Node.js 版本（如 v22.16.0），不是 Electron 版本
- 实际 Electron 版本可以通过 `node -e "console.log(require('electron/package.json').version)"` 查看

### React Router v7

项目中用了 React Router v7，路由匹配规则和 v6 一致。
使用 `HashRouter`（不是 `BrowserRouter`）因为 Electron 使用 `file://` 协议加载页面可能有问题。

## 9. 编译构建

### 修改后必须重新编译的场景

| 修改了 | 需要操作 |
|--------|---------|
| electron/*.ts | `npx.cmd tsc -p tsconfig.electron.json` + 重启 Electron |
| core/*.ts | `npx.cmd tsc -p tsconfig.electron.json` + 重启 Electron |
| core/dictionary/*.json | 无需编译，运行时读取；但如果改路径需要重编译 |
| core/profile/*.ts | `npx.cmd tsc -p tsconfig.electron.json` + 重启 Electron |
| src/*.tsx（React） | 无需编译，Vite 自动热更新 |
| src/types/*.ts | 如果被 electron/ 使用，需要重新编译 |
| test-fixtures/* | 无需操作，测试直接读取 |

### 编译成功但 Electron 启动报错

如果 tsc 编译成功（无报错），但 Electron 启动异常：
1. 检查 `dist-electron/electron/main.js` 是否是最新编译的（看文件修改时间）
2. 尝试 `npm test` 看是否测试通过
3. 如果测试通过，可能是环境变量或路径问题

## 11. React 渲染进程中的 useMemo 陷阱

### 闭包变量遗漏

在 `KeyboardVisualizer.tsx` 的 `keyStateMap` useMemo 中，如果重构时删除了某个局部变量（如 `hasFunckey`），但 `map.set()` 的返回值中仍然引用它，TypeScript 不会报错（因为返回值类型是宽松的 `KeyState`），但运行时会抛出 `ReferenceError`。

**预防措施：** 每次修改 useMemo 内部代码后，检查返回值对象中引用的所有变量都在闭包作用域内有定义。

### ResizeObserver 在 React 中的正确使用

```typescript
// ✅ 正确用法
useEffect(() => {
  const el = ref.current;
  if (!el) return;
  const observer = new ResizeObserver((entries) => {
    for (const entry of entries) {
      setWidth(entry.contentRect.width);
    }
  });
  observer.observe(el);
  return () => observer.disconnect(); // 必须清理
}, []);
```

注意：
- `observer.observe(el)` 和 `observer.disconnect()` 必须配对
- ref 在 effect 执行时可能为 null，需要 guard
- 回调中调用 setState 会触发重渲染，避免在回调中做复杂计算

## 12. React key 与 _overridden 绑定

HotkeyMap 的叠加模式下，会创建带 `_overridden` 后缀 ID 的绑定（如 `reserved_id + '_overridden'`）。
这些绑定作为独立的 React 元素存在，如果不在传递给 KeyboardOccupancy 和 HotkeyList 时过滤掉它们，
会导致：
- 键盘上同一物理键出现重复的绑定显示
- 表格中出现重复行

**解决方案：** 在传 props 之前用 `filter((b) => !b.id.endsWith('_overridden'))` 过滤。

## 13. CSS transform scale 与滚动容器配合

键盘响应式使用了 `transform: scale(n)` 配合 `overflow-x: auto`。

**关键点：**
- `transform-origin` 必须设置（`top left` 或 `top center`），否则缩放后位置偏移
- `overflow-x` 容器拿到的是缩放前的尺寸，需要配合 `min-width` 确保滚动条正确出现
- `will-change: transform` 可以避免缩放时的闪烁
- `-webkit-overflow-scrolling: touch` 提供触屏顺滑滚动

## 14. 命令行环境变量在 Electron 启动时序中的问题

`$env:VITE_DEV_SERVER_URL` 必须在**启动 Electron 的同一命令行会话**中设置。如果在不同的 PowerShell 窗口中设置，另一个窗口中的 Electron 进程不会继承它。

**症状：** Electron 启动后加载 `file://` 路径，页面空白。

**排查方法：** 在 Electron DevTools 的 Console 中输入 `location.href`，如果显示 `chrome-error://chromewebdata/` 说明环境变量设置不正确。

## 15. ALLEGRO_BUILTIN_COMMANDS 必须保持唯一权威来源

`core/validator/commandClassifier.ts` 导出的 `ALLEGRO_BUILTIN_COMMANDS` 集合是内置命令白名单的**唯一权威来源**。

`core/skill/commandRegistry.ts` 通过 `import { ALLEGRO_BUILTIN_COMMANDS }` 导入使用。**不允许在两个文件各自维护独立的命令列表。**

**原因：** 两个列表会不可避免地发生差异。某些命令（如 `cmgr`、`saveas`、`opengl`、`shade`）如果在 classifier 中缺失，会被错误分类为 `unknown` 或关联到不相关的 Skill。

**规则：**
- 如果增加 Allegro 内置命令，**只写到 `commandClassifier.ts` 的 `ALLEGRO_BUILTIN_COMMANDS` 中**
- `commandRegistry.ts` 不需要修改，自动获取最新的内置命令列表
- 添加命令时注意同时保留单字命令（如 `drill`）和多字命令（如 `nc drill`）

## 16. 状态栏 lastLoadTime 状态管理

状态栏使用 `lastLoadTime` 状态记录最后扫描时间，在 `loadAll()` 的 `finally` 块中设置。

**注意：** `setLastLoadTime(new Date())` 必须在 `setLoading(false)` 之后设置，确保加载完成后才更新时间戳。如果放在 `try` 块中，catch 分支抛异常时可能不会更新。

## 17. 来源修正按钮的可见性条件

快捷键详细表格中的 🔧 修正命令来源按钮，条件为 `!binding.isSourceOverridden`（非已修正状态），而**不是** `binding.commandSource === 'unknown'`。

**规则变更原因：** 用户可以对任意绑定进行来源修正，不限于未识别命令。例如用户可能希望将某个自动识别为 Skill 的命令手动改为 "Allegro 内置"。

**注意：** 如果 `isSourceOverridden` 为 `true`，则按钮不显示。用户可以通过后续的编辑弹窗修改来源（编辑弹窗中始终显示命令来源下拉选择）。

## 18. 大写字母不再被当作 Shift 修饰键（V2.2 → V3.0）

### V2.2 变更
`normalizeKey()` 不再将大写单字母（A-Z）自动归入 Shift 层。

| 版本 | `normalizeKey("S")` 结果 |
|------|------------------------|
| 旧行为 | `{ modifiers: ["Shift"], displayKey: "Shift+S" }` |
| V2.2+ | `{ modifiers: [], displayKey: "S" }` |

**原因：** 在 Allegro env 中，`funckey S "command"` 定义的是大写字符 S，不是 Shift+S。

### V3.0 图层系统重构

**ActiveLayer 类型变更：**

| 版本 | 类型值 |
|------|--------|
| V2.2 | `'lowercase' \| 'uppercase' \| 'ctrl' \| 'alt' \| 'shift'` |
| V3.0 | `'normal' \| 'uppercase' \| 'ctrl' \| 'alt' \| 'special'` |

**函数重命名：** `filterBindingsByLayer()` → `filterHotkeysByKeyboardLayer()`

**切换逻辑变更：** 新增 toggle 行为。`handleLayerChange` 不再直接 setLayer，而是：
```typescript
setActiveLayer(prev => prev === layer ? 'normal' : layer);
```
点击已激活的图层按钮 → 回到普通层（而不是无响应）。

**UI 对应关系：**

| 图层按钮 | V2.2 ActiveLayer | V3.0 ActiveLayer | 过滤条件 |
|---------|-----------------|-----------------|---------|
| 普通 | `lowercase` | `normal` | modifiers=[] 且 caseVariant≠"upper" |
| 大写 | `uppercase` | `uppercase` | modifiers=[] 且 caseVariant="upper" |
| Ctrl | `ctrl` | `ctrl` | modifiers 包含 Ctrl |
| Alt | `alt` | `alt` | modifiers 包含 Alt |
| 特殊/Shift | `shift` | `special` | modifiers 包含 Shift（不含 Ctrl/Alt）或 layer==="special" |

## 19. filterHotkeysByKeyboardLayer 与 filterBindingsByLayer / matchesModifiers 的差异

| 函数 | 版本 | 位置 | 说明 |
|------|------|------|------|
| `matchesModifiers()` | V1 | `keyNormalizer.ts` | 旧版修饰键匹配（已弃用） |
| `filterBindingsByLayer()` | V2.2 | `hotkeyItem.ts` | 旧版图层过滤（V3.0 已重命名） |
| `filterHotkeysByKeyboardLayer()` | V3.0 | `hotkeyItem.ts` | **当前版本**，替代上述两者 |

**V3.0 过滤逻辑（`filterHotkeysByKeyboardLayer`）：**

| 图层 | 过滤条件 |
|------|---------|
| `normal`（普通层） | `mods.length === 0 && cv !== 'upper'` |
| `uppercase`（大写层） | `mods.length === 0 && cv === 'upper'` |
| `ctrl` | `mods.includes('Ctrl')` |
| `alt` | `mods.includes('Alt')` |
| `special`（特殊层） | `item.layer === 'special' \|\| (mods.includes('Shift') && !mods.includes('Ctrl') && !mods.includes('Alt'))` |

**注意：** `matchesModifiers` 仍然在 `keyNormalizer.ts` 中保留，但快捷键页面已不再直接使用。

## 20. 默认/保留键数据来源（V2.2 → V3.0）

**核心规则：** 默认/保留键数据来自 `public/data/default_reserved_keys.json` 参考库文件，不是从 env 文件解析出来的。

**错误做法：** 期望 `parseEnvFile()` 或 `validateHotkeys()` 返回保留键数据。

### V2.2 旧方式（废弃）
```
data/default_reserved_keys.json
  → core/dictionary/reservedKeyLoader.ts (fs.readFileSync)
  → electron/ipc/hotkey.ipc.ts (hotkey:get-reserved IPC)
  → preload (getReservedBindings)
  → HotkeyWorkspacePage
```
**问题：** `path.resolve(__dirname, '../../../data/...')` 在编译后路径解析失败。

### V3.0 新方式（当前）
```
public/data/default_reserved_keys.json
  → 前端 fetch('/data/default_reserved_keys.json')
  → loadHotkeyWorkspaceData 解析为 HotkeyBinding[]
  → reservedBindings state
  → getVisibleHotkeysByViewMode
```
**优点：** 不依赖 Electron IPC 和 `fs.readFileSync`，Vite 自动将 `public/` 复制到 `dist/`。

**JSON 加载失败时的表现：**
- 页面显示黄色警告：`默认/保留键参考库加载失败，请检查 public/data/default_reserved_keys.json 是否存在。`
- 保留键视图显示为空（不报红）
- 功能不中断，用户快捷键仍正常显示

**统计数据口径：**
- "我的快捷键"视图：仅统计 env/Profile 绑定的快捷键
- "默认/保留键"视图：仅统计 `public/data/default_reserved_keys.json` 中的条目
- "全部叠加"视图：统计两者之和，同时显示覆盖风险数量

## 21. PhysicalKeyBindingPanel 的绑定过滤

`PhysicalKeyBindingPanel` 接收的 `bindings` 是父组件 `selectedDetail` 计算的结果（使用 `allPhysicalKeyBindings` 属性——视图模式已过滤但修饰键层未过滤的数据），面板内部再通过 `filterHotkeysByKeyboardLayer` 做「仅当前层」的二次过滤。

**数据流：**
```
HotkeyWorkspacePage.sharedState.bindings (viewMode-filtered, modifiers-unfiltered)
  → KeyboardVisualizer.allPhysicalKeyBindings prop
  → selectedDetail (filtered by physicalKey via matchesPhysicalKey)
  → PhysicalKeyBindingPanel.bindings prop
  → (internal) filterHotkeysByKeyboardLayer if "仅当前层" mode
```

**常见错误：** 如果在 PhysicalKeyBindingPanel 中看不到某条绑定，检查：
1. 该绑定是否在 `visibleBindings` 中（视图模式过滤）
2. 是否开启了「仅当前层」且当前图层不匹配
3. 该绑定的 `type` 是否为 `funckey`（alias 不映射物理键）

## 22. 多 env 来源的坑（V3.0）

### 22.1 解析参考 env 时的 ID 冲突

当从参考 env 加载绑定到前端时，参考 env 的 binding `id` 可能与用户 env 的 binding `id` 重复（因为 `validateHotkeys()` 生成的 ID 可能相同）。

**解决：** 合并前用 `ref_${envSourceId}_${b.id}` 格式重新生成 ID。

### 22.2 参考 env 绑定只读

参考 env 中的快捷键被标记为 `editable: false` 和 `status: 'reserved'`。按钮条件依赖这些标记：

```typescript
// 正确：检查 editable 和 bindingSource
if (binding.editable !== false && binding.bindingSource !== 'install_default_env') {
  // 显示编辑按钮
}

// 错误：只检查 bindingSource === 'user_env_original'
// 会漏掉 'install_default_env'、'site_env'、'company_env' 等新来源
```

**所有操作按钮的条件都必须检查 `editable` 字段**，不要依赖特定 `bindingSource` 值。

### 22.3 Apply Plan 只修改活动 env

所有 `generateEditPlan`、`generateAddPlan`、`executeEditPlan` 的 `filePath` 参数必须传递当前活动 env 路径，不能传参考 env 路径。

```typescript
// 正确
const result = await window.atm.generateEditPlan(editData, binding, envSources.activeEnvPath);

// 错误 — 绕过参考 env 保护
const result = await window.atm.generateEditPlan(editData, binding, referenceEnvPath);
```

### 22.4 跨 env 覆盖不是冲突

用户 env 与参考 env 有相同 rawKey 但不同 command 时，`validateHotkeys()` 会生成 `cross_env_override` 类型的 Conflict（info 级别），不会显示为红色错误。

**UI 显示规则：**
- `cross_env_override` → info 级别，蓝色或灰色显示
- `funckey_duplicate` 在同一个 env 中 → error 级别，红色显示

不要混淆这两者。用户覆盖默认是预期行为，不是配置错误。

### 22.5 设置文件写入原子性

`atm_settings.json` 使用 `.tmp` + `rename` 原子写入模式。如果写入过程中进程崩溃，最多丢失一个 `.tmp` 文件，不会破坏原设置。

### 22.6 扫描器路径去重

`scanEnvSources()` 使用 `addedPaths` Set（小写归一化）避免同一路径被重复添加。
如果 `HOME` 和 `USERPROFILE` 指向同一目录（某些 Windows 配置中），不会重复。

### 22.7 安装默认 env 可能不存在

不是所有 Allegro 安装都有 `share/pcb/text/env` 文件。某些版本使用 `env.dat` 或其他文件名。
扫描器会同时检查 `env` 和 `env.dat`，但如果没有安装默认 env，`install_default_env` 来源为空，不影响功能。

### 22.8 路径中中文和空格

`scanEnvSources.ts` 使用 `path.normalize()` 处理所有路径。Node.js 的 `fs.existsSync` 和 `fs.readFileSync` 在 Windows 上原生支持 Unicode 路径，中文和空格不需要特殊处理。

**已验证的路径类型：**
- `C:\Users\张三\pcbenv\env`（中文用户名）
- `D:\Cadence Projects\SPB_Data\pcbenv\env`（空格路径）
- `\\server\share\env`（网络路径）

## 23. 变更历史撤销的注意事项（V4.0）

### 23.1 撤销只恢复文件，不恢复应用状态

`undoLastChange()` 只负责将目标文件恢复到备份版本，**不会**自动重启 Allegro 或刷新页面状态。

**用户需要手动刷新页面**（点击 🔄 刷新按钮）来重新加载快捷键数据。

### 23.2 连续撤销的限制

目前只支持**逐次撤销**（每次撤销最近一次可撤销的变更）。不支持跳转到指定版本。

如果要恢复到较旧的版本，需要连续多次撤销，每次撤销都会：
1. 备份当前文件（用于重做）
2. 从备份恢复目标文件
3. 标记原记录为不可撤销

### 23.3 备份文件保留策略

备份文件保存在 `atm_generated/backup/` 目录，**不会自动删除**。变更历史保留最近 100 条记录。

如果磁盘空间不足，需要手动清理 `atm_generated/backup/` 目录。

### 23.4 撤销后编辑再撤销的序列

```
初始状态 → 修改 A（备份 a1） → 修改 B（备份 b1） → 撤销 B（备份 b2，恢复 b1） → 修改 C
```

此时：
- 最后一次"撤销 B"是可撤销的（恢复 b2）
- "修改 A"不再可撤销（因为备份 a1 和 a1 的记录已被覆盖）
- 如果需要恢复到 A 状态，只能通过连续撤销

## 24. 增强冲突检测的坑（V4.0）

### 24.1 same_env_duplicate vs funckey_duplicate

两者看起来相似但逻辑不同：

| 类型 | 检测条件 | 触发场景 |
|------|---------|---------|
| `funckey_duplicate` | 同一 envSourceId + 同 key + 不同 command | 单文件内重复 |
| `same_env_duplicate` | 同上（V4.0 增强版） | 增加 suggestions 和 involvedFiles |
| `cross_env_override` | 不同 envSourceId + 同 key + 不同 command | 用户 env 覆盖参考 env |

**注意：** `validateHotkeys.ts` 仍然保留，`enhancedConflictDetector.ts` 在它基础上做增强。两者不是替代关系，后者会合并前者的结果。

### 24.2 忽略列表只保存在 localStorage

冲突忽略列表保存在浏览器的 `localStorage`，**不是持久化到磁盘**。

- 清除浏览器数据后会丢失忽略列表
- 切换电脑或重新安装后忽略列表为空
- 目前没有"取消忽略"的 UI，如果需要恢复忽略的冲突，清除 localStorage 或调用：
  ```typescript
  localStorage.removeItem('atm_conflict_ignore');
  ```

## 25. 推荐可用键位的限制（V4.0）

### 25.1 推荐结果不考虑 Allegro 内部占用

推荐算法只检查当前 env 绑定 + 保留键参考库 + Profile 绑定，**不会**检测 Allegro 软件运行时的内部快捷键占用（例如某些 Allegro 命令在特定模式下占用的键）。

**建议：** 推荐的键位在实际使用前仍需在 Allegro 中验证是否可用。

### 25.2 F1-F5 被强制排除

F1-F5 虽然在参考库中标记为 `warnWhenOverride`，但在推荐算法中被**直接排除**（不会出现在推荐列表中），即使当前 env 中没有占用也不推荐。

这不是技术限制，而是用户习惯期望——F1-F5 在几乎所有的 Windows 应用中都有默认功能。

### 25.3 大写字母推荐条件

大写字母（A-Z）只有在以下两种情况才会出现在推荐列表：
1. 对应小写字母已被占用（如 `s` 已绑定 → 推荐 `S`）
2. 作为 Ctrl/Alt 组合键的一部分（Ctrl+S）

单独的大写字母不受推荐，因为大多数用户习惯用小写字母设置快捷键。

## 26. 导出速查表的限制（V4.0）

### 26.1 HTML 导出为独立文件

生成的 HTML 是**完全独立**的文件，没有外部 CSS/JS 依赖。所有样式内嵌在 `<style>` 标签中。
好处是可以直接用浏览器打开，但缺点是样式调整需要修改 `hotkeyExportService.ts`。

### 26.2 快捷键显示"去重"逻辑

导出时将同命令、同类型、同物理键的大小写变体合并显示为一行：
```
s / S → slide     （合并大小写）
Ctrl+S → slide    （单独显示，因修饰键不同不合并）
```

合并规则：
1. 同一物理键（如 S/s）
2. 同一命令（如 slide）
3. 同一类型（funckey）
4. 无修饰键
→ 合并为 "s / S"

如果命令不同（s→slide, S→snap），不合并，各自独立一行。

## 27. window.atm 类型声明的坑（V4.0）

### 27.1 必须集中管理类型

V4.0 前，每个页面（HotkeyPage / DashboardPage / SkillPage）都各自声明 `declare global { interface Window { atm: {...} } }`。

**问题：** 不同页面声明了 `atm` 的不同方法子集。当多个页面同时编译时，TypeScript 报 `Subsequent property declarations must have the same type` 错误。

**解决（V4.0）：** 集中到 `src/types/window.d.ts`，所有页面删除各自的 `declare global` 块。

### 27.2 新增 IPC 时必须更新 window.d.ts

在 `electron/preload.ts` 中新增 `ipcRenderer.invoke('xxx:yyy')` 后，必须同步更新 `src/types/window.d.ts` 的类型声明。

**如果不更新：** 页面和组件代码无法通过 TypeScript 编译，报 `Property 'xxx' does not exist on type...`。

**检查清单：**
1. `electron/ipc/xxx.ipc.ts` — 注册 `ipcMain.handle`
2. `electron/ipc/index.ts` — 注册新模块
3. `electron/preload.ts` — 暴露 API
4. `src/types/window.d.ts` — 更新类型声明

## 28. V4.0 Env 文件导入的坑

### 28.1 安装默认 env 不应合并进用户 env

从 Allegro 安装目录（CDSROOT）导入的 `install_default_env` 类型文件，系统会自动选择「作为参考 env」模式，**不建议**将其合并到用户 env 或方案中。

**原因：**
- 安装默认 env 包含大量全局默认绑定，合并后会造成冗余
- 这些绑定是 Allegro 出厂配置，覆盖它们没有实际意义
- 参考模式可以查看对比，不影响用户环境

**如果要查看安装默认配置：** 使用「作为参考 env」模式，之后在快捷键页面的参考 env 视图中查看。

### 28.2 unknown 类型需要手动确认角色

当系统无法识别导入文件的来源时，会将其标记为 `unknown` 角色，此时**不会自动选择导入模式**，需要用户手动确认。

**常见场景：**
- 从网络路径或 U 盘导入的 .env 文件
- 文件名不是标准的 `env`（如 `my_backup_env.txt`）
- 文件路径不在已知的 Cadence 目录结构中

**操作建议：**
- 如果文件来自个人备份 → 选择「导入为新方案」
- 如果文件来自其他 Allegro 安装 → 选择「作为参考 env」
- 如果希望选择性合并部分绑定 → 选择「高级合并到用户 env」

### 28.3 高级合并必须先预览 Apply Plan

「高级合并到用户 env」模式允许逐条选择要合并的快捷键，但**最终操作必须通过 Apply Plan 执行**。

**常见错误：**
- 用户选择「覆盖」后以为立即生效 → 实际上需要点击「预览 Apply Plan」→ 确认 → 执行
- 直接关闭冲突弹窗 → 所有选择丢失，不会生效

**正确流程：**
```
选择冲突解决 → 点击"预览 Apply Plan" → 查看修改影响 → 确认执行 → 备份 → 写入
```

### 28.4 导入不会覆盖已有 env 绑定

无论选择哪种导入模式，导入操作**不会直接覆盖**用户当前 env 文件中的已有绑定。

**冲突处理规则：**
- 默认策略：保留用户 env 原绑定，跳过冲突项（safe 模式）
- 选择「覆盖」：通过 Apply Plan 将用户 env 中的绑定替换为新绑定
- 选择「跳过」：保持原绑定不变
- 所有覆盖操作生成 Apply Plan，确认后备份再执行

**特别注意：** 覆盖操作执行后，原绑定可以通过变更历史撤销恢复。

### 28.5 导入预览不读取 allegro.ilinit

`buildEnvImportPreview()` 只解析 .env 文件本身，**不会**加载该 env 文件所属环境的 allegro.ilinit 或其他关联配置文件。

**因此预览中显示的 Skill 加载状态可能不完整。** 如果你导入的 .env 文件中包含指向 Skill 命令的快捷键，需要额外检查目标环境中是否已安装这些 Skill。

### 28.6 大文件导入的性能

当导入的 .env 文件包含大量绑定（200+ 行）时，`buildEnvImportPreview()` 和 `computeImportConflicts()` 的计算可能耗时 1-3 秒。

**UI 表现：** 导入预览弹窗会显示加载旋转指示器，计算完成后自动显示结果。

**不影响功能：** 解析在大文件上仍然是同步的，但弹窗 UI 不会阻塞主界面（通过异步 IPC 通信）。

## 29. 快捷键管理页审计常见问题（V4.0 代码审计修复）

2026-06-23 完成了快捷键管理页的 15 区域代码审计，发现 7 个 bug。以下记录审计中发现的典型问题和修复经验。

### 29.1 EnvImportDialog 中 unknown 类型 env 的选择死循环

**问题：** 当导入的 env 文件角色（identifiedRole）为 `unknown` 时，用户选择非参考模式（如"导入为新方案"）会弹出角色确认弹窗。确认后，`handleModeSelect` 直接设置 `selectedMode`，而 `getDefaultMode()` 在 `selectedRole` 未更新时仍返回 `as_reference`。因为 `selectedMode` 初始化使用了 `getDefaultMode(preview.identifiedRole)`，确认后 `selectedMode` 重新计算又回到 `as_reference`，导致无限循环。

**修复：** `handleModeSelect` 将用户的选择存入 `pendingMode`，不直接设置 `selectedMode`。角色确认后，在 `handleRoleConfirm` 中一并设置 `selectedMode` 为 `pendingMode`，打破循环。

**教训：** 异步角色确认与模式选择耦合时，不要让状态设置分两处独立执行。用挂起（pending）变量暂存用户意图，等待前置条件满足后统一设置。

### 29.2 EnvImportDialog 的硬编码路径

**问题：** `handleConfirmApplyPlan` 中使用了硬编码路径 `pcbenvPath + '/env'` 作为 Apply Plan 的目标文件路径。如果用户 env 文件名不是 `env`（或路径包含反斜杠），Apply Plan 会写入错误的位置。

**修复：** 新增 `userEnvFilePath` prop，从父组件 `HotkeyWorkspacePage` 传入真实的 `envInfo.envFilePath`。`handleConfirmApplyPlan` 使用 `userEnvFilePath || pcbenvPath + '/env'` 作为安全回退。

**教训：** 涉及文件写入的路径一定从用户环境获取，不要拼接路径。路径拼接在跨平台时也有隐患（`/` vs `\`）。

### 29.3 EnvImportDialog 冲突处理缺少推荐键位选项

**问题：** 冲突处理 `<select>` 选项列表缺少 `use_recommended_key`（改用推荐键位）。当用户冲突的目的是按键冲突时，改键比改命令更合理，但下拉菜单中找不到这个选项。

**修复：** 在 `<select>` 中添加 `<option value="use_recommended_key">改用推荐键位</option>`。

**教训：** UI 组件的选项列表要与功能枚举保持同步。新增枚举值时检查所有 UI 引用点。

### 29.4 HotkeyMap 收藏筛选未生效

**问题：** `layerUserBindings` 和 `layerReservedBindings` 的 `useMemo` 中，filter 条件没有检查 `showFavoritesOnly` 和 `favoriteIds`。用户点击"仅收藏"按钮后，收藏筛选对 Layer 2 快捷键地图不生效（Layer 1 键盘和 Layer 3 表格正常工作）。

**修复：** 在两个 useMemo 的 filter 回调中增加 `showFavoritesOnly` 和 `favoriteIds` 的判断条件，同时在依赖数组中添加这两个变量。

**教训：** 同一页面中，不同层的相同语义筛选（收藏筛选）需要在所有层独立实现。全局筛选状态变量必须在所有使用它的 useMemo 依赖数组中声明。

### 29.5 BINDING_SRC_CONFIG 缺少 reference_env 和 menu_accelerator

**问题：** `hotkeyItem.ts` 的 `BINDING_SRC_CONFIG` 缺少 `reference_env`（参考 env）和 `menu_accelerator`（菜单加速键）两个来源类型的配置条目。导致这两个来源的绑定在 UI 上显示异常的标签或回退到默认显示。

**修复：** 在 `BINDING_SRC_CONFIG` 中添加：
```typescript
reference_env: { label: '参考 env', className: 'source-tag source-tag--default' },
menu_accelerator: { label: '菜单加速键', className: 'source-tag source-tag--builtin' },
```

**教训：** `BINDING_SRC_CONFIG` 是标签配置的单一来源，新增 BindingSourceType 时必须在配置表中同步添加条目。

### 29.6 BINDING_SRC_CONFIG 重复定义

**问题：** `HotkeyEditor.tsx` 和 `HotkeyMap.tsx` 各自定义了独立的 `BINDING_SRC_CONFIG`（和 `CMD_SRC_CONFIG`）副本。这些副本与 `hotkeyItem.ts` 中的共享配置不一致——当共享配置更新时，重复副本不会被同步更新。

**修复：**
- `HotkeyMap.tsx` — 删除本地的 `BINDING_SRC_CONFIG` 和 `CMD_SRC_CONFIG` 定义，改为从 `hotkeyItem.ts` 导入
- `HotkeyEditor.tsx` — 删除本地的 `BINDING_SRC_CONFIG` 定义，改为从 `hotkeyItem.ts` 导入

**教训：** 共享标签配置必须放在一个文件（`hotkeyItem.ts`），其他组件统一 import，禁止复制粘贴。复制粘贴会在维护时造成不一致。

### 29.7 审计经验总结

| 检查项 | 建议 |
|--------|------|
| useMemo 依赖数组 | state 变量必须出现在依赖数组和 filter 条件中，缺一不可 |
| 路径拼接 | 凡涉及文件写入的路径都从用户环境获取，禁止硬编码 |
| 配置单来源 | 标签、枚举、选项列表等配置数据统一放在一个位置，禁止副本 |
| 异步流程状态 | 涉及多步确认的流程用 pending 变量暂存用户意图 |
| 枚举值与 UI 同步 | 新增枚举值后检查所有 select/dropdown 和 switch 语句 |

## 30. Allegro 动态菜单 API 使用约束

### 30.1 `axlUIMenuRegister` 的第一个参数不是新菜单标题

**问题：** `axlUIMenuRegister(t_command/x_location ll_menu)` 的第一个参数表示插入位置，而不是待创建菜单的显示名称。把 `"ATM Tools"` 或中文菜单标题直接作为第一个参数，只有在同名命令恰好存在时才可能定位成功。

**修复：** ATM 菜单生成器使用 `axlUIMenuFind(nil -1)` 定位菜单栏位置，再通过 `axlUIMenuInsert(... 'popup label)` 创建顶级菜单。

### 30.2 菜单触发器必须使用两参数签名

**问题：** `axlTriggerSet` 的签名是 `axlTriggerSet(s_trigger s_function)`，菜单回调还必须接收一个菜单名参数。三字符串写法 `axlTriggerSet("main" "menu" "callback")` 不符合官方接口。

**修复：** 使用 `axlTriggerSet('menu 'atmMenuOnLoad)`，并定义 `procedure(atmMenuOnLoad(menuName) ...)`。

### 30.3 不要在菜单触发器中调用 `axlUIMenuRegister`

官方文档明确警告不要从 `axlTriggerSet` 回调内部调用 `axlUIMenuRegister()`。复杂动态菜单应在菜单回调中直接使用 `axlUIMenuFind()` 与 `axlUIMenuInsert()`。

### 30.4 重载前只删除自己保存的菜单 ID

直接再次插入会产生重复菜单，按菜单位置盲删又可能删除 Allegro 或公司菜单。ATM 保存自己创建的顶级 `menuId`，手动执行 `atmLoadMenus` 时只删除这些 ID；当 Allegro 加载全新主菜单时，旧 ID 已失效，应先清空记录再构建。

### 30.5 菜单栈最多 8 层

`axlUIMenuInsert` 的官方菜单栈深度限制为 8。ATM 在菜单树校验和 IL 生成两个入口同时拦截超过 8 层的启用可见菜单，避免生成运行时必然失败的配置。

## 31. 配色方案模块

### 31.1 flex column 容器会把子项压成细条而不是滚动

**问题：** 右侧图层列表（`.color-layers-groups`）使用 `display: flex; flex-direction: column; max-height: 560px; overflow-y: auto`。图层多（498 行）时，子项默认 `flex-shrink: 1` 会被压缩进 560px 容器内，行全部变成细条、无法滚动，而 `scrollHeight` 恰好等于 `clientHeight`，看起来像是"内容被折叠"。

**修复：** 给子项 `.color-layer-group` 设置 `flex-shrink: 0`，让内容溢出容器并由 `overflow-y: auto` 滚动。

**避免：** 只检查页面是否有横向溢出或滚动条；要核对滚动区 `scrollHeight > clientHeight` 以及子项实际高度。

### 31.2 `axlLayerGet` 返回对象的 `visibility` 属性不可靠

**问题：** 捕获脚本用 `lp->visibility` 读取图层可见性，实测全部返回 nil，导致 498 个图层全部显示"隐藏"。

**修复：** 使用官方 API `axlIsVisibleLayer("CLASS/SUBCLASS")` 判断可见性，`axlLayerGet` 只用于取颜色等属性。

**避免：** 依赖 layer DBID 上未经验证的字段名；可见性以 `axlIsVisibleLayer` / `axlVisibleGet` 为准。

### 31.3 局部更新方案必须保留图层与调色板元数据

**问题：** `colorUpdateScheme` 合并图层时若只写入 `{ className, subclassName, colorIndex }`，会把目标图层的 `visible`、`layerType` 覆盖丢失；调色板条目只写 `{ index, rgb }` 会丢掉 `name`。

**修复：** 合并时以已有条目为基底：图层保留 `className/subclassName` 并扩散补丁；调色板保留原 `index` 并合并补丁。页面层把完整 `ColorLayerEntry` / `ColorPaletteEntry` 传给 IPC。

### 31.4 单层自定义颜色不能连带改变共享同一索引的其他图层

**问题：** 给 `ETCH/TOP` 输入自定义 Hex 时，如果直接改写该层当前 `colorIndex` 对应的调色板颜色，所有共享该索引的图层都会变色。

**修复：** 按 `createCustomLayerColorPlan` 优先级分配：先找调色板中相同 RGB 复用；当前索引仅由目标图层使用时安全改写；否则占用一个未被任何图层使用的索引；没有安全空位时拒绝并提示，不覆盖其他图层。
